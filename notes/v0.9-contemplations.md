## A. 上下文机制（Context Layering）

### A.1 当前 v0.7 现状

- `blobs` 表存"任意 bytes"，有 trust_label
- `artifacts` 表存"命名产物"（kind / schema_ref）
- `task_links` 表存"task ↔ artifact 多对多"
- 上下文没有"分层"概念，只是一条 blob 流
- Claude Code 的上下文压缩、cache、auto-compact 没有在 harness 层表达

### A.2 需要分层的四层

```text
L0 raw_blob         原始字节（web fetch response, file read, etc.）
                    trust_label 由 ingest 决策

L1 distilled        提取/规范化后的语义单元
                    例：URL → {title, snippet, canonical_url, trust_label}
                    例：long text → {summary, key_facts, trust_label}
                    触发：kernel 在 tool 返回时由 distill worker 异步处理

L2 working_set      当前 task 的"活跃上下文"
                    例：本次 task 累计读了哪些 L1 单元
                    例：累计 token 数 / 剩余 budget
                    强制：超过 budget 时按策略裁剪（最近 LRU / 摘要压缩）

L3 handoff          task 切换/hand-off 时压缩的状态
                    例：把 working_set 蒸馏成可恢复的 handoff blob
                    触发：cancel / reaper / driver 重启 / 长 task 跨上下文边界
```

### A.3 与 Claude Code 上下文机制的对应

| Claude Code 机制 | Harness 层对应 | 落地位置 |
|-----------------|---------------|---------|
| 200K context window | `working_set` budget 字段 | `tasks.budget_cents` 或新 `tasks.context_budget_tokens` |
| auto-compact | `L2 → L3` 蒸馏 | new `distill_worker`（不在 v0.7 scope） |
| cache breakpoints | `L1` 单元 idempotency | `blobs.sha256` 已经提供去重 |
| tool result truncation | `L0 → L1` 蒸馏 | 同上 |
| sub-agent context | `L2 working_set` per attempt | `task_attempts.context_snapshot_blob_id` |
| file @-mention | `L3 handoff` 持久化 | `task_links` role='handoff' |

### A.4 关键不变量（候选）

- **I11**: `working_set` token 总数 ≤ `context_budget_tokens`（强制，由 kernel 拒绝超 budget 写入）
- **I12**: `L1` 蒸馏 idempotent at `sha256`（同 input 产出同 distilled blob_id）
- **I13**: `L3 handoff` 必须可在新 attempt 恢复完整 L2 working_set
- **I14**: cross-attempt handoff 必须带 trust_label（防止信任污染）

### A.5 需要新增的 Protocol / 表

- 新表 `context_snapshots(task_id, attempt_id, level, blob_id, token_count, created_at)`
- 新 Protocol `ContextDistiller(distill(blob) -> distilled_blob, snapshot(working_set) -> handoff_blob)`
- 新 Protocol `ContextBudget(remaining(task_id) -> int, charge(task_id, tokens) -> bool)`
- WorkflowPack 暴露 `context_requirements`（声明本 pack 需要多少 working_set budget）

## B. 负载均衡（Load Balancing Across Workers / Servers）

### B.1 当前 v0.7 现状

- 单进程 SQLite + WAL（spec § PRAGMA）
- 没有 worker pool / 多进程 / 多机协调
- Codex v0.7 §3 也只验证单连接 race，没考虑跨 worker
- v0.6 PRD 提到"Worker 池"但没具体设计

### B.2 需要分层的四层

```text
L0 task_dispatch   task 创建 → 选 worker
                    策略：round-robin / least-loaded / capability-match / cost-aware
                    落点：新增 `worker_pool` Protocol

L1 worker_lifecycle  worker 注册 / 心跳 / 退役
                    强制：worker 必须周期 renew lease_token；超时即被 reaper 标 stale
                    落点：`workers` 新表 + `worker_heartbeat` 事件

L2 cross_server    跨 host 的 worker 协调
                    例：local-host:5 worker + remote-host:3 worker
                    挑战：fence_version 是全局还是 per-server？
                    答案：per-server（task.fence_version 已经是 task-local 计数器）

L3 graceful_drain  worker 退役 / 服务器维护
                    触发：drain_request → kernel 暂停派发 → 等 active 完成 → 退出
                    强制：active attempt 持有 lease_token，drain 不强制 kill
```

### B.3 关键不变量（候选）

- **I15**: 每个 task 最多一个 active attempt，跨 server 也成立（靠 partial unique index）
- **I16**: worker 的 lease_token 必须周期性 renew；超过 lease_expires_at 的 attempt 必须被 reaper 处理
- **I17**: drain 期间不再派发新 task 给该 worker；active attempt 允许完成或被 cancel
- **I18**: 跨 server 的 attempt 创建必须靠 SQLite WAL 同步（要么同 host，要么 SQLite 集群方案）

### B.4 需要新增的 Protocol / 表

- 新表 `workers(worker_id, host, capabilities_json, status, last_heartbeat_at, current_attempt_id)`
- 新 Protocol `WorkerPool(dispatch(task) -> worker_id, heartbeat(worker_id, attempt_id, lease_token), drain(worker_id))`
- `spec/state-transitions.md` §1.1 claim 改成 "worker_pool.dispatch → claim"
- 新 spike `spikes/m0/worker-dispatch-test.py`：双 worker 池 + 公平性测试

### B.5 风险与开放问题

- **R1**: SQLite WAL 在 NFS / 跨 host 上有可靠性问题 → 是否要换 Litestream / rqlite / TiDB？
- **R2**: fence_version 是 task-local 计数器；如果两个 server 同时 dispatch 同一个 task，靠 partial unique index 兜底，但 dispatch 的 latency 可能浪费（一个是 noop）
- **R3**: worker 心跳 vs lease 续约是同一个还是不同？v0.7 把 lease 写在 attempt 表里；worker 心跳应该单独表
- **R4**: graceful drain 是否支持 SIGTERM 优雅？需要约定 SIGTERM 行为

## C. 与 v0.7 / v0.8 现状的关系

| v0.7/0.8 已实现 | v0.9 增量 |
|------------------|----------|
| SQLite 是单一事实来源 | 不变；worker_pool 仅是 dispatch 层，不破坏单一事实 |
| lease_token + fence_version | 不变；新 `workers` 表与 attempt 关联（worker_id 已存在） |
| spec/state-transitions.md §1.6 reaper | 扩展：worker-level reaper（worker stale → 不再派发） |
| spikes/m0/claim-fence-test 跨进程 race | 扩展：跨 host race（file-level SQLite 共享） |
| conformance-second-impl 6 Protocol | 新增 2 Protocol：ContextDistiller, WorkerPool（仍 runtime_checkable） |
| M1 硬门槛 1（kernel schema）| 扩展：context_snapshots + workers 表进 schema |
