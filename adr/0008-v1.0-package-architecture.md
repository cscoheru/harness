## Context

v0.9-B 阶段的交付物是 **spec baseline + spike suite**：

- `spec/kernel-schema.sql`（873 行，schema + 6 trigger invariants）
- `spec/interfaces/*.py`（10 个 Protocol 定义）
- `spec/events/*.json`（12 个事件 schema）
- `spikes/m0/`（13 spike，5627 行，含 `_helpers.py` 530 行 reference）

v0.9-B 没有 production runtime：`pip install -e .` 不可用；`import harness` 不存在；Dockerfile / deploy workflow 都没有。

v1.0 GA 的目标 = 把 v0.9-B 升级为「可生产部署的 runtime」。T-BE-1..5 + T-TG-1..5 完成后 `harness/` package 引入 5 个 subpackage，每个 subpackage 必须有明确的：

1. **职责边界**（什么代码属于这里，什么不属于）
2. **生产 ownership**（哪一个 v0.9 spike 文件是它的 source-of-truth）
3. **版本对齐**（spec 改动必须同步改对应 production 实现）

如果不文档化：

- **drift 风险**：`_helpers.py` 与 `harness/runtime/_db.py` 容易双源分叉
- **复用边界模糊**：新 contributor 不知道在 `_helpers.py` 加新功能还是 `harness/runtime/_db.py` 加
- **依赖方向模糊**：`gateway` 是否能反向依赖 `drivers`？`testing` 是否能反向依赖 `runtime`？

GA plan §7 已锁定「`_helpers.py` 与 `harness/runtime/` 共存」，但**共存不等于双源**——必须有明确的 ownership。

## Decision

`harness/` package 5 subpackage 布局如下：

| Subpackage | 职责 | v0.9 spike ownership | 关键 production 类 / 函数 |
|------------|------|----------------------|----------------------------|
| `harness/runtime/` | Kernel 后端：DB、worker 注册与派发、context lineage、event sink | `spikes/m0/_helpers.py`（530 行） | `SqliteWorkerPool` / `SqliteEventSink` / `SqliteContextManager` / `_db.py`（make_db / connect_with_fk / seed_task / claim_via_pool） |
| `harness/gateway/` | 6-step tool invocation chain + egress + artifact | `spikes/m0/conformance-second-impl.py`（545 行，RealGateway）+ `spikes/m0/egress-httpx-actual.py`（219 行，PinnedResolver） | `ToolInvocationGatewayImpl` / `HttpEgressService` / `PinnedResolver` / `RealArtifactStore` |
| `harness/drivers/` | ExecutionDriver 实现（v1.0 stubs） | `spikes/m0/conformance-second-impl.py`（TrivialDriver，190 行） | `CodexSdkDriver` / `CodexExecDriver`（共享 `StubDriverBase`） |
| `harness/testing/` | 集成测试 + mutation suite + stress test fixture | `spikes/m0/mutation-test.py`（999 行）+ `spikes/m0/egress-httpx-actual.py`（echo server） | `mutation_suite.py`（17/17）/ `stress_test.py`（50×200）/ `echo_server.py`（127.0.0.1 fixture）/ `InProcessEgressServer` |
| `harness/benchmark/` | Throughput + latency benchmark runner | 新建（v1.0） | `runner.py`（p99 < 5000 ms gate; JSON + optional CSV output） |

### 复用规则（binding）

1. **`spikes/m0/_helpers.py` 不可删**（GA plan §7 + 用户硬规则）。它是 `harness/runtime/_db.py` + `worker_pool.py` 的 **canonical reference**——发现 bug 先修 spike，再同步生产实现。
2. **`spikes/m0/conformance-second-impl.py` 不可删**。它是 `harness/gateway/gateway.py` + `harness/drivers/{codex_sdk,codex_exec}.py` 的 canonical reference。
3. **`spikes/m0/mutation-test.py` 不可删**。它是 `harness/testing/mutation_suite.py` 的 canonical reference。
4. **生产代码不反向依赖 spike**：`harness/runtime/*.py` 不能 `import spikes`。反之 spike 可以 `import harness.*` 来验证 production 与 reference 行为一致。

### 依赖方向图（强约束）

```text
harness/runtime/      (无 harness 内部依赖)
harness/gateway/      → harness/runtime/ (仅 EventSink + WorkerPool types)
harness/drivers/      → harness/runtime/ (仅 EventSink types)
harness/testing/      → harness/{runtime,gateway,drivers}/ (全可达)
harness/benchmark/    → harness/runtime/ (具体实现 + WorkerPool/EventSink
                    SQLite 接口)；模块内部对 Sqlite* 类保持依赖以便
                    写入 SQLite WAL / 读 results.json — **不是** 仅
                    依赖抽象 Protocol
```

**反向依赖禁令**：
- `harness/runtime/` 不得 import `harness/gateway/` / `harness/drivers/` / `harness/testing/` / `harness/benchmark/` — 保持 kernel 零依赖
- `harness/gateway/` 不得 import `harness/drivers/`（driver 是 gateway 的下游 consumer，不是反过来）
- `harness/drivers/` 不得 import `harness/gateway/` / `harness/testing/` / `harness/benchmark/`
- `harness/benchmark/` 不得 import `harness/testing/`（避免 metric 与 test fixture 互相污染）

### 版本对齐

- `pyproject.toml` `version = "1.0.0a0"` 必须与 `CHANGELOG.md` `[v1.0.0a0]` 段一致
- `spec/` 内任何 Protocol 改动必须同步更新对应 production 实现 + spike reference，三处 PR 同步 merge
- spike suite (`spikes/m0/*.py`) 与 `harness/` package 行为零变化（per T-BE-1 acceptance — `conformance-second-impl.py` 10/10 Protocol 持续全绿）

### 出口协议（10 Protocol）

`harness/__init__.py` 显式 export 10 个 Protocol：

```python
from harness import (
    WorkerPool, EventSink, ContextDistiller, ContextBudget,
    ContextManager, ArtifactStore, ToolInvocationGateway,
    ToolProvider, PolicyDecisionPoint, ExecutionDriver,
)
```

注：Protocol 实际类名是 `PolicyDecisionPoint`（`spec/interfaces/policy_decision.py`），
同模块的 `PolicyDecision` 是 `PDP.evaluate()` 返回的 *frozen dataclass*（位于
`spec/interfaces/tool_provider.py`），两者是 distinct types — `harness/__init__.py`
不 re-export dataclass。`WorkflowPack` 是 data-only（per README §3），不在 10 Protocol
出口范围——它通过 `WorkerPool.dispatch(pack)` 间接参与 runtime，无需直接 import。

## Alternatives Considered

- **A1: 单 `harness/` 包，无 subpackage** — 简单但失去职责边界；`gateway` 与 `runtime` 互相污染；~3500 行单包难以维护。拒绝。
- **A2: spike 删掉，只留 `harness/`** — 失去 canonical source-of-truth；mutation suite 的 17/17 + conformance 的 10/10 需要新写 reference 实现；v0.9 → v1.0 不向后兼容。**用户硬规则禁止删 spike**。拒绝。
- **A3: 保留 spike 但 spike 引用 `harness/`** — 失去 spike 的 reference 角色（spike 应该是 reference 而非依赖者）。拒绝。
- **A4: 6 subpackage（增加 `harness/types/`）** — 当前 5 subpackage 已覆盖；新增 `types/` 会和 `spec/interfaces/` 重复。**保留 5 subpackage**。

## Consequences

- ✅ **职责清晰**：新 PR 一眼看出属于哪个 subpackage；code review 按 subpackage 走
- ✅ **双源防 drift**：`spike` 是 canonical reference；production 实现必须 pass spike 验收
- ✅ **kernel 零依赖**：`harness/runtime/` 可单独打包（极端场景：只有 SQLite backend）
- ✅ **依赖方向可静态检查**：未来可加 `import-linter` 或 `pydeps` 在 CI gating
- ❌ **多一层抽象**：`harness/runtime/_db.py` 几乎等于 `_helpers.py` lift；早期开发显得冗余
- ❌ **subpackage 间通信成本**：`gateway → runtime` 必须经 Protocol 类型而非直接 import class
